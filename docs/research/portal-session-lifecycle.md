# RemoteDesktop session lifecycle and KDE indicators

Research date: 2026-11-16. Source inspection only; no desktop reproduction or application changes. The reported screenshot was not attached to this research request, so its exact indicator count, ownership, and installed KDE version remain unverified.

## Findings

An active RemoteDesktop session legitimately grants desktop input control even when used only for keyboard delivery. KDE's official implementation shows a status notifier when starting a session and labels it “Remote Control”; its description depends on the requested devices. An expected security indicator must remain visible. Repeated indicators can represent multiple legitimate sessions, abandoned sessions, separate processes, or a backend/UI problem; the screenshot alone cannot distinguish them. [KDE start and notifier](https://github.com/KDE/xdg-desktop-portal-kde/blob/ab5e5cbaf5bce73bd437ea29363197d764503a63/src/remotedesktop.cpp#L223), [notifier title](https://github.com/KDE/xdg-desktop-portal-kde/blob/ab5e5cbaf5bce73bd437ea29363197d764503a63/src/remotedesktop.cpp#L633).

The strongest application-side finding is a cleanup gap: our current broker drops ashpd session wrappers on errors, but **ashpd 0.13.13 does not implement `Drop` for `Session` and does not automatically send `Session.Close`**. Its shared D-Bus connection survives those wrapper drops. Consequently, reconnecting can leave older portal sessions alive. This is a credible leak mechanism, not a confirmed diagnosis of the reported desktop. [Versioned Session source](https://docs.rs/crate/ashpd/0.13.13/source/src/desktop/session.rs), [shared connection source](https://docs.rs/crate/ashpd/0.13.13/source/src/proxy.rs).

## Official lifecycle contract

- Create a session, select devices, then start it. The resulting session is a long-lived portal object, not a per-keystroke operation. Applications can end it using `Session.Close`; backend closure is reported through `Session.Closed`. Closing ends associated user interaction. [RemoteDesktop lifecycle](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html#session-lifecycle), [Sessions](https://flatpak.github.io/xdg-desktop-portal/docs/sessions.html), [Session API](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Session.html).
- `ConnectToEIS` follows `Start`, may be called only once per session, and the session should be closed when EIS disconnects. A retry therefore needs a new session after ending the old one, rather than reconnecting EIS on the existing session. [ConnectToEIS](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html#org-freedesktop-portal-remotedesktop-connecttoeis).
- A restore token restores authorization/configuration during a new session setup; it is not an active session handle or an instruction to suppress indicators. Tokens are single-use and replaced by the token returned from `Start`. Invalid tokens fall back to normal prompting. Persist mode 2 persists permissions until revoked, not the live control channel indefinitely. [SelectDevices persistence options](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html#org-freedesktop-portal-remotedesktop-selectdevices).

## Our implementation

Source: [portal_input.rs](../../reader/crates/readerd/src/portal_input.rs), especially `run` (line 92), `request` (207), and `Connection::connect` (235). Dependency version: [Cargo.lock](../../Cargo.lock), ashpd 0.13.13.

| Concern | Observed behavior | Implication |
| --- | --- | --- |
| Ownership and reuse | A process-local `BROKER` starts one serialized worker with separate `keyboard` and `pointer` connection slots; successful actions reuse their slot. | Repeated successful actions should not create sessions each time. One process can intentionally hold two live RemoteDesktop sessions after both capability paths are used. |
| Action failure or cancellation | Any action error sets the selected slot to `None`, even if failure occurred before actual input delivery. Idle pumping also clears disconnected slots. | Wrapper/socket destruction occurs, but there is no explicit portal close. The next action recreates the slot and can add a session. |
| Partial setup | `CreateSession` precedes directory creation, device selection, Start, token persistence, EIS connection, and handshake; each later operation can fail or be canceled. | Every post-create error needs session cleanup, including token-write and handshake failures. A session need not reach the stored `Connection` to require cleanup. |
| Cancellation and timeout | `request` polls the portal future with cancellation checks and a 60-second deadline; cancellation drops that future. | Local future cancellation does not itself prove `Request.Close` or `Session.Close` reached the portal. Cancellation while CreateSession is in flight needs special handling because the remote session can exist before its wrapper is returned. |
| Retry | No same-action replay after uncertain delivery; a later action reconnects when the slot is empty. | Preserve this delivery safety rule while making session teardown explicit before replacement. |
| Persistence | Separate keyboard and pointer token files; fresh tokens are written after Start. | Two token files are permission records, not proof of two currently active sessions. Deleting a token does not close a live session. |

There is no explicit `Session::close()` call or `Drop` implementation in this module. In the pinned ashpd source, `Session::close` is an async D-Bus call (lines 76–85); `Request::close` is a separate async call (lines 270–282). The process-wide `OnceLock<zbus::Connection>` in `proxy.rs` (lines 27–42) rules out relying on the last per-session wrapper to disconnect the bus. [Session source](https://docs.rs/crate/ashpd/0.13.13/source/src/desktop/session.rs), [Request source](https://docs.rs/crate/ashpd/0.13.13/source/src/desktop/request.rs), [Proxy source](https://docs.rs/crate/ashpd/0.13.13/source/src/proxy.rs).

Claims that “ashpd asynchronously closes sessions on Drop” do not apply to this pinned version. More generally, even a library that spawns async cleanup from a synchronous destructor would not provide an awaited close result or guaranteed completion during executor/process shutdown. For deterministic cleanup, retain the handle and await explicit close on cancellation, failed setup, disconnect, replacement, and orderly shutdown. An async Drop fallback would supplement that ownership policy, not establish it.

## Speed of Sound and Stargate comparison

Inspected Speed of Sound revision `c233281cdcc4407b5f648de41fceef90dca849cc`, which pins Stargate **0.6.0**. Stargate tag `v0.6.0` resolves to inspected revision `e624aebf837841984b2d7626611f379df9cfb67c`. [Dependency declaration](https://github.com/zugaldia/speedofsound/blob/c233281cdcc4407b5f648de41fceef90dca849cc/gradle/libs.versions.toml#L28), [Stargate release source](https://github.com/zugaldia/stargate/tree/v0.6.0).

- Speed of Sound owns one `PortalsClient`, containing one `DesktopPortal`; it requests keyboard only with persistent permissions. Input uses the active session rather than starting one for every character. Its manager tracks disconnected state, observes Closed, and attempts reconnect when disconnected and supported. It distinguishes user cancellation from unsupported/error status and clears saved tokens on start failure. [PortalsClient](https://github.com/zugaldia/speedofsound/blob/c233281cdcc4407b5f648de41fceef90dca849cc/core/src/main/kotlin/com/zugaldia/speedofsound/core/desktop/portals/PortalsClient.kt#L31), [session manager](https://github.com/zugaldia/speedofsound/blob/c233281cdcc4407b5f648de41fceef90dca849cc/app/src/main/kotlin/com/zugaldia/speedofsound/app/portals/PortalsSessionManager.kt#L76).
- This is a useful ownership pattern, **not proof that Stargate guarantees one live server session**. `RemoteDesktopPortal.startSession` always creates a session and overwrites the active handle; on select/start failure it calls `clearSession`. `PortalSession.clear` only sets its local handle to null. These paths do not call the portal's Session.Close, and no guard in `startSession` prevents creating another session while one is active. [startSession](https://github.com/zugaldia/stargate/blob/e624aebf837841984b2d7626611f379df9cfb67c/sdk/src/main/kotlin/com/zugaldia/stargate/sdk/remotedesktop/RemoteDesktopPortal.kt#L161), [local handle management](https://github.com/zugaldia/stargate/blob/e624aebf837841984b2d7626611f379df9cfb67c/sdk/src/main/kotlin/com/zugaldia/stargate/sdk/session/PortalSession.kt#L23).
- Canceling Speed of Sound's event collector removes signal observation; its manager's `shutdown` only cancels that job. Stargate's `observeClosed` cleanup removes the signal handler, whereas `DesktopPortal.close` closes the underlying bus connection. These are distinct from an explicit Session.Close. Do not equate canceling a coroutine or clearing a handle with terminating remote control. [manager shutdown](https://github.com/zugaldia/speedofsound/blob/c233281cdcc4407b5f648de41fceef90dca849cc/app/src/main/kotlin/com/zugaldia/speedofsound/app/portals/PortalsSessionManager.kt#L125), [observer cleanup](https://github.com/zugaldia/stargate/blob/e624aebf837841984b2d7626611f379df9cfb67c/sdk/src/main/kotlin/com/zugaldia/stargate/sdk/session/PortalSession.kt#L94), [DesktopPortal.close](https://github.com/zugaldia/stargate/blob/e624aebf837841984b2d7626611f379df9cfb67c/sdk/src/main/kotlin/com/zugaldia/stargate/sdk/DesktopPortal.kt#L60).

## Interpretation and follow-up evidence

Keep one deliberate owner per capability policy and reuse its successful session. Combining keyboard and pointer into one owner/session is a possible product decision, but expands the devices requested together; the current two-slot policy can legitimately yield two indicators. Before any implementation change, correlate session object paths, D-Bus sender names, process IDs, create/start/close results, and action cancellation/failure timestamps without logging tokens or typed content.

The singleton broker is per process, not system-wide. Separate readerd instances, another application using RemoteDesktop, or another input-owning process can each contribute sessions. Session paths include the caller's unique bus name, so matching application names or icons cannot establish a common owner. [Session handle identity](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Session.html).

A stable count consistent with intentional owners is expected. Growth after failures/retries in one owner, with old session paths still live and no successful Close, supports a leak. Indicators that survive confirmed session teardown require backend/UI investigation. KDE's session close handler disconnects its EIS cookie, providing an additional observable teardown boundary. [KDE close handling](https://github.com/KDE/xdg-desktop-portal-kde/blob/ab5e5cbaf5bce73bd437ea29363197d764503a63/src/remotedesktop.cpp#L152). No runtime conclusion or recommendation to hide security indicators follows from this source-only investigation.
