# Recorded actions

Researched 2026-11-16 against primary documentation and upstream source. Recommendations below are design proposals, not verified desktop behavior.

## Recommended contract

Replace the single advance key with a versioned **recorded action**: an ordered list of physical key down/up events with monotonic offsets. Default: one Space down followed by Space up (choose an explicit short duration, for example 40 ms). Keep the existing configured post-action delay independent: start it after the final release; never store it inside the recording.

Record opens and focuses a dedicated keyboard recording panel. Arm after the activation key has been released, so Enter/Space used to activate Record is excluded. Esc or Stop finishes; reserve Esc and exclude its down/up events. Preserve overlapping keys, left/right modifiers, event order and all internal gaps. Normalize the first accepted down to time zero and end at the last release: waiting before the first event or before clicking Stop contributes no duration. Empty recording leaves the previous action intact.

Stop should finalize only a balanced sequence. If keys remain held, stop accepting new downs and wait briefly for their real releases while the panel stays focused; on timeout or focus loss, discard the draft and retain the previous action. Do not invent release times and call them recorded timing. Provide a separate Cancel operation that discards the draft.

## Focused browser recording

Use trusted `keydown`/`keyup` events in the recording panel, with `KeyboardEvent.code` as physical identity, `location` for diagnostics, `repeat` explicitly retained, and event timestamps plus stable insertion order. `key` is a display label, not a physical replay identifier. The W3C defines physical codes and distinguishes repeated keydown from keyup; keyboard event targets follow focus. Thus this records events delivered to the focused panel, not arbitrary desktop input. Browser/compositor reserved shortcuts, IME processing and unavailable/empty codes prevent a promise to record every possible key. Reject unsupported codes/composition instead of guessing. [UI Events](https://www.w3.org/TR/uievents/#events-keyboardevents), [physical code specification](https://www.w3.org/TR/uievents-code/)

While armed, prevent default actions for accepted keys (Space scrolling, Tab focus traversal); preserve a reachable Stop control and accessible recording status. Disarm and discard on panel/window blur, hidden document, navigation or lost capture state: a release may otherwise go to a different focus target. Track a pressed set; reject unmatched releases and modifiers already held when recording begins. A modifier boolean on another event is not evidence of its missing down time. Store no events outside the explicit recording interval.

## Windows and AutoHotkey v2

`InputHook("L0")` disables text accumulation. `KeyOpt("{All}", "N")` enables both down/up notifications; callbacks receive VK and SC, and execute as new AHK threads. `NotifyNonText` alone misses ordinary text keys. End keys do not invoke `OnKeyDown`, so Esc handling needs an explicit termination policy. `Stop()` ends the hook. The hook is installed at desktop scope, so it is **not inherently focus-limited**: start only for the recording UI, gate every callback by foreground identity and stop on blur. `S` suppresses keys; visibility settings alone exempt modifiers. `MinSendLevel` cannot filter all injected input; SendInput/SendPlay are ignored, while non-AHK injection is not excluded by that setting. [Official InputHook documentation source](https://github.com/AutoHotkey/AutoHotkeyDocs/blob/v2/docs/lib/InputHook.htm)

Replay validated physical events using explicit scan-code down/up sends. AHK SendInput ignores `SetKeyDelay`; preserve timing with a scheduler between sends, not one concatenated send string. `{Blind}` avoids implicit modifier release/restoration and menu masking but also preserves physically held modifiers: require a neutral physical modifier state before playback. Repeated down events are distinct from holding a key; AHK documents that a synthetic hold does not itself auto-repeat. [Official Send documentation source](https://github.com/AutoHotkey/AutoHotkeyDocs/blob/v2/docs/lib/Send.htm)

Win32 SendInput inserts events serially, retains existing keyboard state, and is constrained by UIPI to equal/lower integrity targets. Check the inserted-event count; partial delivery must not trigger automatic replay. Scan-code injection requires correct extended-key flags; Windows scan codes, DOM codes and Linux evdev codes are different namespaces. Never cast between them. [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput), [KEYBDINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput)

## Wayland playback and capture

RemoteDesktop requires CreateSession → SelectDevices(KEYBOARD) → Start, which requests authorization and reports granted devices. `NotifyKeyboardKeycode`/`NotifyKeyboardKeysym` accept released=0 and pressed=1; these are injection methods, not listeners. Keysyms express symbols, not physical identities. Prefer the existing EIS sender: ConnectToEIS is version 2, follows Start and is called once per session. Once connected, Notify methods must not be mixed into that session. Restore tokens request permission restoration; they do not guarantee authorization or availability. Close canceled sessions, handle denial/revocation and session closure, and complete permission setup before choosing the target focus or starting the playback clock. [RemoteDesktop specification](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html)

EI keyboard requests use Linux `input-event-codes.h`/evdev codes, **without the XKB +8 offset**. Use an explicit allowlisted DOM-code mapping, preserving sides and keypad identity (Space=57, left Ctrl=29, right Ctrl=97). Where symbol semantics are desired, resolve against the advertised device keymap instead. Frame each transition; the protocol forbids multiple requests for the same key within one frame. Release keys before stop_emulating. Observe device resume/pause/removal rather than assuming a usable keyboard forever. [EI keyboard protocol](https://libinput.pages.freedesktop.org/libei/interfaces/ei_keyboard/index.html), [libei sender API](https://libinput.pages.freedesktop.org/libei/api/group__libei-sender.html)

Keep repeat metadata distinct from physical transitions. Windows can replay repeated downs; the inspected EI keyboard API exposes state transitions without a repeat-timing contract. A held key may cause downstream repeat under compositor/client settings. Therefore exact browser auto-repeat timing across Wayland playback remains unproven: initially reject repeat-containing recordings on that backend with a clear explanation, rather than silently converting repeats into extra taps. Verify held-key behavior against the supported compositor/client versions before claiming fidelity.

RemoteDesktop EIS is a **sender** connection. A receiver context requires separately authorized capture support; changing libei mode does not grant access. InputCapture redirects input during compositor activation, supports capability negotiation and EIS reception, and uses an enable/activate/deactivate lifecycle, commonly with pointer barriers. It is not a portable passive background keyboard observer. Use ordinary focused browser events for this feature; do not require global capture, privileged input devices or compositor-specific recording hooks. [libei architecture](https://libinput.pages.freedesktop.org/libei/api/), [InputCapture specification](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.InputCapture.html)

## Desktop support and existing seams

- **KDE Plasma:** current portal source implements Notify keyboard methods and ConnectToEIS through KWin; its InputCapture implementation separately uses KWin's EIS capture manager. This establishes upstream implementation, not availability on every installed Plasma version. Probe granted keyboard capability and EIS device readiness at runtime. [RemoteDesktop source](https://github.com/KDE/xdg-desktop-portal-kde/blob/master/src/remotedesktop.cpp), [EI adapter](https://github.com/KDE/xdg-desktop-portal-kde/blob/master/src/eiconnection.cpp), [InputCapture source](https://github.com/KDE/xdg-desktop-portal-kde/blob/master/src/inputcapture.cpp)
- **Hyprland:** current upstream `master` portal descriptor includes InputCapture but omits RemoteDesktop. Capture source connects through its dedicated input-capture protocol. Do not infer playback support from capture support or screencasting. The existing RemoteDesktop/EIS playback path needs a compatible backend selected on the host; report unavailable capability instead of silently bypassing authorization. Installed releases can differ from upstream. [Portal descriptor](https://github.com/hyprwm/xdg-desktop-portal-hyprland/blob/master/hyprland.portal), [capture implementation](https://github.com/hyprwm/xdg-desktop-portal-hyprland/blob/master/src/portals/InputCapture.cpp)

Local inspection: [portal_input.rs](../../reader/crates/readerd/src/portal_input.rs) already serializes authorized EIS actions, saves keyboard restore tokens, avoids retry after uncertain delivery and releases a chord in reverse order even after cancellation. Its `Action::Key`/`keys()` sends a chord immediately; it cannot represent recorded timing or arbitrary release order. Extend that broker with a bounded event sequence rather than looping through its chord API. [read_along_capture.rs](../../reader/crates/readerd/src/read_along_capture.rs) supplies a KDE active-window guard; it is optional outside KDE, so it does not establish portable Wayland target safety.

## Implementation acceptance criteria

Use explicit platform mappings and backend validation before saving. Suggested initial bounds: 256 events, 30 seconds total, 10 seconds maximum internal gap; reject oversize input instead of truncating. Validate monotonic finite offsets, known codes, balanced transitions and repeat policy on the backend as well as the UI. These limits and the default hold duration are product choices.

Schedule against absolute monotonic deadlines to avoid accumulating sleep drift; timestamps in protocol frames do not replace waiting before transmission. Keep waits cancellable and pump EIS events. Check target focus before each down and throughout long gaps. Foreground injection cannot atomically bind delivery to a window; a focus check still races, and generic Wayland supplies no universal active-window inspection. Where a reliable guard is unavailable, expose that limitation or disable unattended playback.

On cancel, timeout, focus loss, device pause, session closure or error, stop new downs and best-effort release only keys owned by this playback, then end emulation/close the session as necessary. Cleanup releases must run even when the ordinary focus guard rejects further input; never release every physical modifier indiscriminately. Never retry a partly delivered sequence. Verify ordering/overlap, trimming, reserved Esc, Stop while held, repeat rejection, mapping, cancellation during gaps, focus changes and authorization loss; native Windows and compositor runtime behavior remain unvalidated by this research.
