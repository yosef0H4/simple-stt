# Process grouping and lifetime

Checked against upstream documentation and the working tree on 2026-11-20.

## Windows

- Task Manager’s **Processes** tab presents apps and background processes. Its **Details** tab shows individual processes and their PIDs. Microsoft describes tab-specific grouping and private data sources, and its public documentation gives no registration method that guarantees one named app row for arbitrary Win32 executables. Chromium’s engineers describe modern Windows grouping Chrome’s processes under the parent task. That is an observation about Chrome, and Simple STT’s row placement still needs to be observed on the Windows version in use. [Task Manager](https://learn.microsoft.com/en-us/troubleshoot/windows-server/support-tools/support-tools-task-manager), [Chromium process model interview](https://chromium.googlesource.com/chromium/src/%2B/refs/tags/140.0.7339.244/docs/transcripts/wuwt-e08-processes.md).
- `AppUserModelID` is the documented Windows shell identity for taskbar buttons, pinning and Jump Lists. A shared ID can group windows from several processes under one taskbar button. Microsoft documents setting matching shortcut and window or process IDs for this purpose. The documentation gives no Task Manager grouping guarantee for this ID. [Application User Model IDs](https://learn.microsoft.com/en-us/windows/win32/shell/appids).
- Windows records parentage when creating a process. A child runs independently, so ending the parent leaves the child's lifetime up to other mechanisms. A Job Object can contain and account for multiple processes. Children created by `CreateProcess` normally inherit job membership, subject to breakaway and nesting rules. `TerminateJobObject` terminates members, and `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` terminates members when the last handle to the job closes. These are documented lifecycle and accounting controls. [Creating processes](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-processes), [Terminating a process](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process), [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

## Linux

- The monitor determines presentation. GNOME System Monitor offers a process-dependency tree. KDE Plasma’s Applications model uses recognized cgroups and can combine cgroups that resolve to the same application ID. Its current upstream implementation considers mappings and conventions such as `app-` units and Flatpak scopes. systemd’s desktop integration guidance describes `app-<ApplicationID>` unit names that can map to `.desktop` entries. A service cgroup is inspectable even when a monitor omits it from its Applications view. [GNOME System Monitor](https://github.com/GNOME/gnome-system-monitor#readme), [KDE application model](https://github.com/KDE/libksysguard/blob/master/processcore/application_data_model.cpp), [systemd desktop conventions](https://systemd.io/DESKTOP_ENVIRONMENTS/), [systemd-cgls](https://www.freedesktop.org/software/systemd/man/latest/systemd-cgls.html).
- Linux children inherit their parent’s cgroup at creation. A systemd service starts its workload through the manager, and a scope groups externally created processes. For a service stop, `ExecStop=` runs first if configured and systemd handles the remaining members according to `KillMode=`. The default `control-group` targets the unit’s cgroup, normally with `SIGTERM` followed by `SIGKILL` for survivors after the stop timeout. Membership can be inspected with `systemd-cgls --user-unit simple-stt-linux.service` or `/proc/PID/cgroup`. [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html#organizing-processes-and-threads), [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html#ExecStop=), [systemd.scope](https://www.freedesktop.org/software/systemd/man/latest/systemd.scope.html), [systemd.kill](https://www.freedesktop.org/software/systemd/man/latest/systemd.kill.html#KillMode=), [systemd-cgls](https://www.freedesktop.org/software/systemd/man/latest/systemd-cgls.html).

## Simple STT today

- **Windows.** The packaged `simple-stt.cmd` starts `AutoHotkey64.exe` with `simple-stt.ahk`. The shell launches and supervises capture, launches short-lived control commands and starts the Settings launcher. The Settings launcher starts the Tauri window process, and WebView2 can provide its own browser, renderer and other helper processes. Normal shell exit requests reader and capture shutdown. Capture has a timed exact-PID fallback for the inference child, and the shell has a timed exact-PID fallback for capture. Those paths give targeted cleanup. An abrupt shell termination can bypass `OnExit`, and the checked-in launch paths provide no Simple STT–owned Job Object covering the desktop workload. [Distribution launcher](../../scripts/build-distribution.ps1), [AHK shell](../../ahk/simple-stt.ahk), [Capture supervisor](../../ahk/lib/ProcessSupervisor.ahk), [Settings launcher](../../src/bin/simple_stt_settings.rs), [Inference supervisor](../../src/capture/inference_supervisor.rs), [WebView2 process model](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model).
- **Linux.** The installed `simple-stt-linux.service` starts the desktop daemon and normally contains its capture and inference descendants. It defines `ExecStop=/usr/bin/simple-stt shutdown`, a 15-second stop timeout and restart on failure. `simple-stt launch` asks the user manager to start the service, then opens Settings from the launcher. Settings opened through the tray is instead spawned by the daemon, so those entry points can land in different cgroups. The on-demand reader controller inherits the lineage and cgroup of the invocation that first starts it. The separate headless API has its own `simple-stt-server.service`. [Desktop service](../../packaging/linux/simple-stt-linux.service), [Linux launcher and daemon](../../src/bin/simple_stt_linux.rs), [Reader startup](../../reader/crates/readerctl/src/main.rs), [Headless API service](../../packaging/linux/simple-stt-server.service).
- **Worker isolation.** Capture starts `simple-stt-infer` on demand and recycles it on idle, unload and shutdown. Inference exits when its input stream closes and it returns to the protocol read loop. A native call can delay that exit, which is why the supervisor uses exact-child termination if graceful shutdown times out. Display grouping leaves the worker’s PID, model ownership and stop policy intact. [Capture shutdown](../../src/bin/simple_stt_capture.rs), [Inference supervisor](../../src/capture/inference_supervisor.rs), [Inference worker](../../src/bin/simple_stt_infer.rs).

The launch and stop findings above come from source inspection. Actual Task Manager rows, Linux monitor rows and per-launch cgroup membership were unverified on a running desktop.
