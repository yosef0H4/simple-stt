# TTS text normalization research

## Findings

- The shipped Sherpa-ONNX 1.13.8 Supertonic frontend performs punctuation replacements, collapses whitespace, adds terminal punctuation and wraps text in a language tag. It then NFKD-decomposes and looks up character IDs. It does **not** implement number-to-words rules: digits are passed to the model indexer, subject to that model's character coverage. This does not establish correct spoken numbers. Supertone says the model learns to read numbers and acknowledges unreliable Turkish examples. [Pinned frontend](https://raw.githubusercontent.com/k2-fsa/sherpa-onnx/v1.13.8/sherpa-onnx/csrc/offline-tts-supertonic-unicode-processor.cc), [upstream issue](https://github.com/supertone-oss-archive/supertonic/issues/144).
- The same pinned frontend replaces `@` with English `at`, and `e.g.,`/`i.e.,` with English phrases regardless of the language tag. It replaces `/`, brackets and several other characters with spaces and removes some symbols. Avoid promising that preserving input in our layer preserves every symbol through the native frontend, including in Arabic. [Pinned frontend](https://raw.githubusercontent.com/k2-fsa/sherpa-onnx/v1.13.8/sherpa-onnx/csrc/offline-tts-supertonic-unicode-processor.cc).
- Sherpa 1.13.8 Kokoro uses its own multilingual lexicon and eSpeak frontend; it is not necessarily equivalent to the upstream Python Misaki frontend. Its source explicitly avoids lowercasing the whole input because this changes phonemizer punctuation handling. A report of Kokoro context-dependent pronunciation differences concerns this model family. A later Sherpa 2.0.1 issue describes dropped numeric/OOV words **after eSpeak removal**; it is not proof that the same failure exists in our 1.13.8 runtime. [Pinned lexicon](https://raw.githubusercontent.com/k2-fsa/sherpa-onnx/v1.13.8/sherpa-onnx/csrc/kokoro-multi-lang-lexicon.cc), [pronunciation issue](https://github.com/k2-fsa/sherpa-onnx/issues/2004), [later frontend issue](https://github.com/k2-fsa/sherpa-onnx/issues/4139).
- Rust [`num2words` 1.2.0](https://docs.rs/num2words/1.2.0/src/num2words/lib.rs.html) supports English, French variants and Ukrainian, **not Arabic**; its default is English. Python's similarly named project supports Arabic, but is a different implementation. [`num2words2-core`'s Arabic port](https://docs.rs/num2words2-core/latest/num2words2_core/lang_ar/index.html) exists, but documents inherited precision and grammatical caveats; its correctness and footprint need independent evaluation before use. No Python runtime is needed for either Rust crate.

## Recommended small first step

1. Offer an opt-in, per-model Kokoro setting to lowercase ASCII letters in the synthesized copy. Explain that this can change acronyms and names (`US` versus `us`); leave it off by default. Keep original text, highlighting and history untouched. Do not apply to Supertonic or remote providers. A narrower caps-only policy may avoid changing mixed-case text but cannot reliably distinguish an uppercase word from an acronym.
2. Select language and model using the original text, then transform the routed speech unit immediately before native synthesis. Route the same setting through desktop, CLI and HTTP rendering, including cached/preloaded paths. Never make routing decisions from normalized words or write them back to source text.
3. Do not add automatic Arabic number-to-English conversion. Prefer unchanged digits until an Arabic-capable normalizer has been checked with native-speaker examples. ASCII, Arabic-Indic `٠١٢٣٤٥٦٧٨٩` and Eastern Arabic-Indic `۰۱۲۳۴۵۶۷۸۹` digits all need explicit handling if conversion is later added; `ar` must never fall through to the English crate default. If an English-only experimental normalizer is added, use an explicit `en` match and operate only on isolated unambiguous integers; preserve Arabic-script/mixed-language runs and unknown language routes.
4. Preserve ambiguous forms: dates (`03/04/2026`), times, decimal/group separators (`1,234`, `١٬٢٣٤`, `٣٫١٤`), currency, percentages, ranges, negatives, leading-zero identifiers, versions, phone numbers and alphanumeric codes. Correct expansion depends on locale, grammar and intent; preserve malformed, oversized or unsupported cases rather than guessing. Markdown, links, email addresses, code and URLs also need source-aware parsing before transforming; don't strip or rewrite them with broad regexes.

## Validation needed before shipping

Unit-test disabled/default behavior, case preservation in displayed original, mixed scripts, Unicode boundaries, routing before transformation, per-model isolation and unchanged ambiguous values. Compare actual generated speech on the bundled Sherpa version for uppercase prose, acronyms, numbers and Arabic examples; ensure persisted options reach all synthesis paths. Native runtime behavior and subjective pronunciation have not been tested in this research.

## Currency follow-up

For the requested `5$` case, offer one opt-in **Read currency amounts** control per local TTS binding, separate from Kokoro's case option. Apply it to the routed synthesis copy only; off retains the existing path. Do not add individual controls for decimals, positions or currency names.

Evidence is limited: the pinned Supertonic preprocessing table has no dollar expansion, so `$5` and `5$` proceed as characters to the model indexer, subject to indexer coverage. Supertone's [historical English example](https://github.com/supertone-oss-archive/supertonic#natural-text-handling) claims successful handling of `$5.2M`, but does not establish the result for our exact runtime, suffix notation or Arabic. In Sherpa 1.13.8 Kokoro non-Chinese text goes through eSpeak/lexicon processing; the sources inspected do not establish the spoken output for either position, decimals or Arabic-Indic digits in our package. A [later 2.0.1 report](https://github.com/k2-fsa/sherpa-onnx/issues/4139) concerns a different frontend. No output was heard for this research.

A cautious first implementation can recognize isolated `$5` and `5$` (optionally separated by whitespace), reorder them as `5 dollars` for an English route, and use `dollar` for 1. Keep the original digit sequence: the model still decides how to pronounce it. `$` identifies a dollar amount, not necessarily a US dollar; do not add a country. Use explicit language selection, never default unknown or Arabic to English. For Arabic, `٥$` → `٥ دولارات` is a candidate for 3–10, but requires native-speaker and actual model checks before enabling. Arabic has separate one, two, few, many and other categories, with few and many also depending on the last two digits; digit order alone does not solve grammar, especially 1, 2 and 11+. [CLDR Arabic plural examples](https://unicode.org/cldr/charts/45/verify/numbers/ar.html). Leaving the original amount for unsupported values is safer than inventing an English phrase. Support ASCII, Arabic-Indic and Eastern Arabic-Indic numerals explicitly if Arabic parsing is introduced.

Require lexical boundaries and skip code spans or blocks, URLs, shell variables such as `$PATH` or `$5` in code, identifiers, adjacent letters, leading zeros, negative values, grouped numbers, decimal separators, ranges and currency/magnitude suffixes. Plain text may lack enough context to distinguish a shell positional parameter from an amount, so an explicit literal/code mode or conservative context handling matters; do not claim universal detection. Leave decimal currency unchanged until locale-specific parsing and minor-unit wording are designed and validated. Test both symbol positions, 0/1/2/3/5/10/11/21/100, both Arabic digit sets, decimals, `US$5`, `$PATH`, fenced/inline code, malformed input and unknown languages, including original display and all speech paths. Compare actual Kokoro and Supertonic playback or transcriptions; this note makes no claim that preserving digits guarantees correct pronunciation.

Implementation now supplies this opt-in for isolated whole dollar tokens on English and Arabic local routes (maximum six digits). Supertonic maps Extended Arabic-Indic digits to ASCII in its synthesis copy; ordinary Arabic-Indic digits stay unchanged. Arabic one and two use explicit phrases, while other values select the dollar noun by the final two digits. No playback verification is implied.

## Default cleanup and punctuation follow-up

The implementation now defaults cleanup on, with a per-binding switch to send literal input to the engine. Its prepared-text display represents application preprocessing only; the native frontend may make further changes. Cleanup replaces an isolated letter/letter token such as `heap/data` with `heap, data`, preserves numeric fractions, URLs, absolute paths, multi-slash paths and backtick spans, and retains other punctuation. A single-slash relative path such as `src/lib` has exactly the same syntax as `heap/data`, so without semantic or source metadata it cannot always be distinguished; use literal mode for code and paths. Lowercasing remains separately optional and runs only when cleanup is enabled. Dollar cleanup defaults on under the main switch.

Punctuation can supply speech pauses rather than being noise: eSpeak documents a special punctuation-speaking mode, while a [Piper issue](https://github.com/rhasspy/piper/issues/122) reports missing expected pauses and a [Read Aloud issue](https://github.com/ken107/read-aloud/issues/515) discusses lost list or symbolic content. These reports motivate retaining sentence punctuation and list clauses instead of deleting all symbols; they do not prove behavior in the packaged models. [eSpeak commands](https://espeak.sourceforge.net/commands.html).

The parent verified the pinned Supertonic binary indexer: Extended Arabic-Indic ۰–۹ map to -1; Arabic-Indic ٠–٩ map to 332–341; ASCII digits map to 17–26; `$` maps to 5 and `@` to -1. The application maps Extended Arabic-Indic digits to ASCII in its speech copy when cleanup is on. Separately, the native frontend rewrites `@` to English `at` even in Arabic. Mapping or preserving a token does not guarantee its pronunciation.

## Isolated acceptance probes

The application spells isolated whole dollar amounts below 100 in Arabic words, with Arabic currency forms; larger whole amounts retain digits. This is separate from general numeric input, dates and decimals, which remain unchanged. Standard Arabic-Indic digits remain supported by the model; only the unsupported Extended Arabic-Indic set is mapped to ASCII outside code.

`scripts/test-tts-pronunciation.py` renders public examples on CUDA and transcribes the saved files with GPU STT, without playing audio. The English probe reproduced “heap slash data” from the original and omitted “slash” from the comma-prepared input. Arabic observations varied between runs, so they are only diagnostics: the lightweight Lemura recognizer prioritizes speed and size, and its transcript is not ground truth for TTS pronunciation. WAVs and observations are retained under ignored `artifacts/combined-app/pronunciation/` for human listening. No human pronunciation acceptance is claimed.
