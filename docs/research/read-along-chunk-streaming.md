# Read-along chunk streaming

Research: 2026-11-16. Recommendations below are proposed changes, not implemented behavior.

## Recommended scheduling contract

- For **every page, including the first**, synthesize units sequentially: feed unit 1 to playback as soon as its first playable PCM arrives, then synthesize units 2, 3, … while playback consumes earlier audio. Never collect all page audio before starting. A provider without incremental audio may finish one short unit first; it still must not finish the whole page first.
- Overlap next-page capture/OCR with current playback, retaining exactly one pending page. Current-page TTS has priority; pending-page OCR readiness does not imply permission to monopolize the shared TTS worker. If spare capacity permits, prepare a bounded prefix of pending audio to reduce handoff silence.
- Promote only after the current page's final audio has actually drained. Transfer the prepared page plan, tags, buffered audio and live producer together; promotion must not reset synthesis or wait for the pending page's full synthesis. If its first audio is late, wait without advancing another page. One-page lookahead reduces gaps but cannot guarantee gapless output when preparation is slower than playback.
- Keep the active page's text/highlight tags visible while pending OCR completes. Each PCM frame retains run/page/unit/sentence/attempt identity; advance the active tag from consumed audio, never from the latest OCR result or synthesis completion.

These are application scheduling recommendations inferred from the queue and streaming sources below; provider support and actual latency require measurement.

## Current seams

- `reader/crates/readerd/src/main.rs`: `start_text_at` / `run_session` already synthesize ordered `SpeechUnit`s into playback; each frame retains sentence/unit IDs. `AudioOutput::push` applies backpressure with a configured 1–8 second sample queue. Keep this behavior for the initial page.
- `PreparedReadAlongPage` currently holds page text, a whole-page `Vec<i16>`, and the last route. `start_read_along_prefetch` calls `collect_routed_media` inside a whole-page retry. That collector plans units, collects each unit, concatenates/resamples into a vector (maximum 300 seconds), and discards metadata through a no-op callback.
- `promote_read_along_page` replans text but pushes all prepared audio as sentence/unit `0/0`. This delays readiness until all synthesis completes and loses alignment. Replace this path with the same tagged streaming playback used by the initial page.
- `reader/crates/readerd/src/read_along.rs`: `Controller` already gates capture/promotion to one pending fingerprint; `Preparation::begin_advance` and cached OCR text survive processing retries. Input delivery deliberately sits outside processing retries because a failure can follow partial delivery. Preserve these invariants.
- The supervisor serializes worker use through its worker mutex. `collect` yields priority at unit boundaries; `synthesize` holds the worker during a unit. Merely starting another thread does not provide two independent synthesis engines. `reader-tts/src/main.rs::synthesize_remote` already emits PCM frames with job, generation, sentence, unit, sample offset, rate, and final flag.
- `reader-core/src/language.rs` performs lazy offline fastText detection with bounded input and confidence checks. `run_session` and `media_routing::unit_route` already support per-unit detection. Retain local detection even when synthesis is remote.

## Primary-source findings

1. Rust [`sync_channel`](https://doc.rust-lang.org/std/sync/mpsc/fn.sync_channel.html) is FIFO and bounded by message count; sending blocks when full. Capacity zero is a rendezvous. A bounded channel therefore needs bounded payloads and a cancellation strategy, not just a small capacity.
2. Tokio [`mpsc`](https://docs.rs/tokio/latest/tokio/sync/mpsc/index.html) supports bounded queues with backpressure and blocking send/receive for synchronous callers. [`Sender::send`](https://docs.rs/tokio/latest/tokio/sync/mpsc/struct.Sender.html#method.send) can lose its owned message if cancelled in `select!`; reserving capacity first retains ownership until commitment. Successful send is not a playback acknowledgement. Use Tokio only if an async orchestration seam is warranted; the existing thread-based daemon can use standard channels.
3. OpenAI's [Speech guide](https://developers.openai.com/api/docs/guides/text-to-speech#streaming-realtime-audio) documents playback before full generation and raw 24 kHz signed 16-bit little-endian PCM. Its official [speech SDK source](https://github.com/openai/openai-python/blob/main/src/openai/resources/audio/speech.py) exposes a streaming response that avoids eager body reads. The official [response implementation](https://github.com/openai/openai-python/blob/main/src/openai/_response.py) provides byte iteration and explicit close. These establish an incremental transport pattern; compatibility with other endpoints must be checked separately.
4. Azure's [speech synthesis documentation](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/how-to-speech-synthesis#subscribe-to-synthesizer-events) distinguishes synthesis data events from word/sentence boundaries and warns that events arrive faster than playback. Transport chunks are not linguistic boundaries. Playback position, not arrival time, must drive highlighting.
5. Azure's [latency guide](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/how-to-lower-speech-synthesis-latency) distinguishes first-byte latency from full synthesis latency and recommends consuming streaming output as it arrives. Measure capture→OCR, OCR→first playable audio, and final-current-sample→first-next-sample separately; whole-page synthesis time alone cannot explain startup or handoff delays.
6. ElevenLabs' [streaming guide](https://elevenlabs.io/docs/eleven-api/guides/how-to/websockets/realtime-tts#buffering) documents text thresholds that delay generation, a quality/latency tradeoff when reducing them, and explicit flushing of a short final tail. It also directs callers with complete input text toward HTTP streaming. Recommendation: segment finalized OCR text at sentence/clause boundaries, with a bounded fallback for long unpunctuated spans; keep the first unit short enough for prompt startup without splitting words or language-specific punctuation blindly. Do not copy provider character thresholds as universal defaults. For a streaming-input provider, explicitly finalize/flush the last text so a short page cannot wait indefinitely below its generation threshold.

## Implementable design

1. Plan each OCR page once into immutable units. Assign stable run ID, page ID, unit/sentence IDs, text ranges, and a frozen route per unit. Store ordered events such as `Audio { unit, chunk_seq, source_sample_offset, sample_rate, pcm }`, `UnitEnd`, `PageEnd`, and `Failed`. Preserve `starts_in_code`, voice/speed and sentence gaps. Byte blocks must be decoded incrementally; keep odd PCM bytes between reads and use a stateful resampler across blocks. Do not resample each block independently.
2. Replace the prepared vector with a page stream handle containing the plan, bounded receiver, cancellation handle, producer state and first playable frame. Promote once this first frame is available and the current page has completed. Transfer the existing receiver/producer into active ownership; do not regenerate or replan the page. Start playback immediately, consume subsequent frames in order, and continue synthesis during playback. Distinguish `first_audio_ready` from `producer_finished`.
3. Maintain exactly two page slots: current and optional pending. After capturing the current snapshot, one guarded advance may expose the next page; OCR and speech preparation can overlap current playback. Never execute another advance or capture a further page while the pending slot is occupied. Only promotion frees that slot. Preserve the prefetch-disabled policy of waiting for current playback before advance/capture.
4. Start with a small bounded frame queue per page (for example four frames capped at 100 ms each) and the existing playback queue. Bound decoded frame allocation, encoded response buffers, OCR/text size, and in-flight jobs too. At 24 kHz mono i16, 400 ms is 19,200 PCM bytes per page queue; this excludes playback buffers, model memory and temporary codec allocations. When pending audio reaches its budget, stop requesting further units until promotion. A paused consumer must backpressure rather than accumulate a page.
5. Schedule current-page synthesis ahead of pending synthesis whenever current buffered audio is below a low-water mark. On the shared local worker, interleave at unit boundaries and release its lease before waiting for pending queue capacity. Otherwise a full pending queue can hold the worker needed to refill current audio until promotion, causing deadlock. For an already-running request, retain only bounded frames and explicitly cancel/restart an entirely uncommitted unit if necessary. Independent remote/local workers may run concurrently, but keep a fixed concurrency budget and one pending page. Shared-worker scheduling cannot guarantee seamless playback if an uninterruptible local unit exceeds the available audio reserve; measure this and keep units short.
6. Use a stable run cancellation token plus per-page tokens. Promotion currently changes `app_generation`; explicitly rebind the promoted consumer without invalidating its producer through a captured old generation. Reject stale run/page/attempt IDs before enqueue, playback and state mutation. Stop must drop receivers, abort remote response reads, cancel worker work and wake audio waits. With `sync_channel`, use `try_send` plus bounded cancellation-aware waits, or ensure receiver teardown unblocks `send`; never join a producer while retaining its full receiver. Avoid holding controller/worker locks across waits.

## Retry, focus and completion rules

- Keep the advance attempt ledger outside OCR/TTS retry scopes. An advance with uncertain partial delivery must not be automatically replayed. Retry OCR from the retained snapshot/selected region without another input action; retain accepted OCR text for synthesis retries.
- Track generated, queued and consumed positions separately. Drop duplicate transport frames by page/unit/attempt/offset before enqueue. A queued frame is already committed for retry purposes even if playback has not reached it. Retry a unit automatically only if none of its PCM has been committed to playback; discard that attempt's buffered frames first. Already completed units remain committed.
- After a unit partially reaches playback, generic TTS regeneration cannot reliably reproduce the same sample offsets. Unless a provider offers a documented resumable stream, stop at that boundary and expose recovery; do not replay its spoken prefix. Continuing from an arbitrary regenerated sample offset is not an exactly-once guarantee. Do not retry the whole page after partial playback.
- Preserve selected-window identity and existing focus checks immediately before each advance action. On focus loss finish current audio, retain at most the pending page and wait for the selected window; do not steal focus. Background preparation from an already valid snapshot need not inject input. Recheck cancellation after focus waits and before capture, promotion and input.
- A temporary empty playback queue is not page completion. Call `audio.finish` only after `PageEnd` and all ordered frames are accepted, then wait for drain. Underflow waits for the producer; it must never trigger promotion or another advance. Promotion atomically consumes the pending handle and updates the controller once.
- Route from the saved configuration/page fallback and each unit's local language result, not the last successfully synthesized unit's mutated configuration. Freeze provider/model/voice decisions so retries do not silently change engines. Normalize differing sample rates while preserving metadata and check cancellation during engine changes.

## Acceptance checks for implementation

Use deterministic fake producers and the existing controller/lifecycle test seams: first PCM plays before producer EOF; delayed later chunks do not complete the page; sentence/unit tags and gaps survive promotion; pending OCR overlaps playback; repeated Next never creates a second pending page; slow/paused playback bounds queues; a full pending queue cannot monopolize the shared worker; stop wakes full-channel and remote-read waits; promotion preserves the producer token; duplicate offsets are rejected; failures before commitment retry without another advance; partial playback never restarts spoken units; local/remote mixed routes preserve order/rates; missing or ambiguous local detection follows configured fallback. Measure first-audio latency, underruns, maximum buffered bytes, pending-page count and cancellation latency. Desktop runtime validation must follow the repository's installed-package workflow.
