# Reading and OCR: user workflows and small UX opportunities

Research checked 2026-11-04. Sources are first-party issue reports, project documentation, and source code. An issue describes one reporter's experience, not prevalence or proof that Simple STT has the same defect. Browser readers are useful workflow evidence, but their document extraction differs from desktop selection and screenshot OCR.

## Existing baseline

The integrated reader already has selection and region actions, clipboard listening, stop, pause/resume, previous/replay/next, a speed setting, automatic language routing and manual model bindings. The controller reports sentence/chunk progress, device, model status, notices and clipboard-listening state. The shell owns shortcuts and the compact native HUD; OCR copy is a separate action. Workers are on demand with independent timeouts and a bounded two-worker speech cache. Settings access does not start an audio device. See [architecture](../architecture.md), [reading settings](../../web/settings/src/pages/Reading.svelte), and [controller implementation](../../reader/crates/readerd/src/main.rs). These are code observations, not desktop validation; inspect actual HUD and platform behavior before treating an opportunity below as a confirmed gap.

## Observations from users and maintainers

- A Read Aloud user reading English mixed with Arabic asked for switching language/voice within one passage, without manually changing voice for every language switch. This is a reported need, not evidence that all mixed-script detection is reliable. [Read Aloud #499](https://github.com/ken107/read-aloud/issues/499).
- A user said the back control repeated multiple sentences when they wanted only the previous sentence. [Read Aloud #489](https://github.com/ken107/read-aloud/issues/489). Simple STT already has sentence navigation; verify its actual boundaries and affordances rather than adding duplicate transport controls.
- Another report describes parts of lists and symbols being skipped during speech. [Read Aloud #515](https://github.com/Read-Aloud/read-aloud/issues/515). The generalizable concern is knowing what was actually read; it does not establish a Simple STT parsing bug.
- Opening a separate highlighted-text view reportedly restarted the reading session. [Read Aloud #513](https://github.com/ken107/read-aloud/issues/513). A view of progress should not itself change playback state.
- A NormCap user reported a cursor loading animation obscuring text in the screenshot; the maintainer suggested moving the pointer before capture and noted screenshot backend limitations. [NormCap discussion #459](https://github.com/dynobo/normcap/discussions/459).
- NormCap's changelog documents fixes for missing line breaks, paragraph parsing and incorrect region selection with Linux display scaling. It also describes raw versus parsed text and screenshot/clipboard backend differences. These are historical project changes, not evidence of current Simple STT defects. [NormCap changelog](https://github.com/dynobo/normcap/blob/main/CHANGELOG).
- One NormCap report describes OCR results not appearing in the clipboard, illustrating that capture, recognition, and delivery are distinct failure points. [NormCap #849](https://github.com/dynobo/normcap/issues/849).
- A CopyQ user reported high CPU and memory after copying large text, including repeated clipboard-read delays and allocation failures; another described clipboard monitoring failing in an XCB-on-Wayland setup. Neither proves this app has the same failure. [CopyQ #3096](https://github.com/hluk/CopyQ/issues/3096), [CopyQ #3587](https://github.com/hluk/CopyQ/issues/3587).
- CopyQ documents ignoring clipboard formats marked secret by password managers and other applications, including platform-specific markers. This is a documented design choice, not a universal guarantee that all sensitive content carries a marker. [CopyQ FAQ](https://github.com/hluk/CopyQ/blob/master/docs/faq.rst#secret-clipboard-data).
- Read Aloud documents selection, pause/play, voice and speed as everyday controls. This supports keeping common controls close to the reading task; its browser implementation is not a desktop benchmark. [Read Aloud basics](https://github.com/ken107/read-aloud/blob/master/docs/usage/basics.md).

## Ranked proposals (inferences, not verified defects)

1. **Recover an OCR result before speaking it.** Trigger: a region returns text. Offer a compact, optional review of the extracted text with editable lines, `Read`, `Copy`, and `Retake`; preserve the recognized order and expose it plainly, especially for Arabic/English, columns and punctuation. Do not promise automatic layout repair or force a dialog on every capture. Existing OCR copy remains available. Evidence: NormCap's line-break history and clipboard failure report. Cost: one bounded text buffer and view only after capture; no new idle worker, polling, GPU or model memory.
2. **Explain and temporarily override the language for this reading.** Trigger: mixed Arabic/English or uncertain detection, or the user hears an unsuitable voice. Show the current route in the existing HUD and offer a session-only Auto / Arabic / English override for the current text or selected span, returning to saved settings next time. Check existing HUD/route APIs first; the app already has automatic per-unit routing and persistent bindings. Evidence: #499. Cost: small metadata and an on-demand route change; no new idle CPU or model preload, though a user-requested switch may load an existing worker and temporarily use its normal bounded cache.
3. **Make clipboard listening safe and legible.** Trigger: user enables listening or copies text while it is enabled. Keep a visible, unobtrusive active indicator and one-click stop; ignore supported secret clipboard markers and show a brief non-content notice when a marked item is skipped. Cap and cancel oversized reads; report unavailable clipboard access instead of silently appearing active. Check platform capabilities and existing state before implementation. Evidence: CopyQ FAQ and #3096/#3587. Cost: marker inspection only on existing clipboard events; no extra idle polling or model load. Some sensitive content is unmarked and cannot be identified reliably this way.
4. **Provide a non-disruptive progress glance.** Trigger: open the existing HUD during an active or paused reading. Show current sentence and a compact position such as sentence 3 of 12; opening or dismissing it must preserve playback and selection. Existing status already exposes sentence and chunk text, so first verify whether the HUD already presents this. Evidence: #489, #513 and #515. Cost: reuse current status; no additional inference or persistent idle activity. Sentence position does not prove every word was spoken.
5. **Give capture a clear escape and retry path.** Trigger: user cancels the region picker, gets an empty result, or screenshot permission/backend fails. Escape should exit without starting OCR; failure notice should distinguish capture from recognition and offer `Retake` with a short hint to move the pointer if it covers text. Validate scaling and multi-monitor selection rather than claiming they are broken. Evidence: NormCap #459 and its changelog. Cost: event-driven messages only; cancel before worker launch when possible, with no added idle memory or polling.

Speed, sentence skip/replay and worker warmth already exist. Before changing them, verify that controls remain responsive during model loading, that playback position is retained, and that the HUD exposes relevant state; these are qualification questions, not claims of defects. None of the above requires a larger permanent control panel. Estimates are architectural expectations, not measurements.

Implementation note: clipboard snapshot handling now skips the KDE secret hint and known Windows privacy formats before reading content. Unmarked sensitive content remains undetectable; verify platform behavior with the native suite. Windows marker semantics are documented by [Microsoft](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-formats).
