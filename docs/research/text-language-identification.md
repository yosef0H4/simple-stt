# Compact offline text language identification

Checked 2026-11-04. The current `whatlang` 0.18 reliability gate abstains on some short inputs, including Arabic greetings. Abstention routes to the configured fallback, so automatic language selection needs to distinguish “unknown” from a positive English identification. Script alone cannot distinguish Arabic from Persian or Urdu.

## Candidate

[fastText's official language identification documentation](https://github.com/facebookresearch/fastText/blob/main/docs/language-identification.md) describes `lid.176.ftz`: 176 UTF-8 language labels, 917 kB, and somewhat lower accuracy than its 126 MB model. Its published language list contains the 31 Supertonic languages, plus unsupported languages such as Persian and Urdu. Its model license is **CC BY-SA 3.0**, not 4.0; attribution, license notice, and the two requested paper citations in the official documentation need to accompany any distributed asset. The separate [fastText code](https://github.com/facebookresearch/fastText) is MIT licensed. The newer NLLB model has a different, noncommercial license and is not this candidate.

The official linked asset `https://dl.fbaipublicfiles.com/fasttext/supervised-models/lid.176.ftz` was downloaded on 2026-11-04 to a temporary location. Its SHA-256 was `8f3472cfe8738a7b6099e8e999c3cbfae0dcd15696aac7d7738a8039db603e83`; this is an observed digest, not an independently published upstream checksum. Pin it and preserve provenance if distributing the exact bytes.

The [`fasttext` 0.8.0 crate](https://docs.rs/crate/fasttext/0.8.0) is a pure Rust implementation, but the primary agent's initial calibration with the official `.ftz` gave implausible results: `مرحبا` classified as Esperanto at 0.99, an English sentence as Hindi, and a Korean sentence as Serbian at 0.999. These observations reject that candidate for this use; the cause has not been established.

The replacement candidate [`fasttext` 0.7.8](https://docs.rs/crate/fasttext/0.7.8) wraps native fastText via `cfasttext-sys`, which builds bundled C++ sources using `cc`. It loads a model by filename; the packaged model must be installed beside the executable. Debug builds can fall back to the checkout asset. This adds a C++ build toolchain requirement and its path handling and Windows builds need validation. The wrapper accepts UTF-8 strings for filenames, while C++ platform file-opening behavior may not handle all Windows Unicode paths. The model is loaded lazily; its disk size does not prove actual resident-memory cost.
## Decision and verification needed

The native candidate uses provisional 0.5 confidence and 0.2 margin thresholds pending calibration. We have not run the native model here: no empirical claim is made that it fixes short Arabic greetings, or that its confidence scores are calibrated. Before integration, the main implementation should measure top candidates and scores for `مرحبا`, `شكرا`, `سلام`, representative Persian and Urdu text, `Hello world`, ambiguous names/numbers, and representative texts of each supported language, including short and longer inputs. Compare unsupported-language handling and confidence/abstention behavior; do not restrict prediction to the supported labels before choosing the winner, since that can force unsupported Persian or Urdu to Arabic. Record cold/warm latency, peak and resident RSS, and quality tradeoffs, including mixed text.

The implementation loads the official file lazily, normalizes whitespace, caps text before prediction, and preserves the winning label even if unsupported so routing can reject it. Low-confidence results are unknown. A threshold and any special handling must follow measured examples, not arbitrary confidence values. Do not add a script-only Arabic heuristic. If short examples still fail, retain a fallback or investigate a different compact model instead of claiming full support. Packaging must include the model attribution and license notices; keep model copies and any language cache bounded.
